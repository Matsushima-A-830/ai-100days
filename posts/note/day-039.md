# Day 039 note原稿 — vercel-labs/agent-browser & agent-desktop

要点3行:
- GitHub Trendingで見かけたVercel Labs製agent-browserを導入しようとしたら、公式の手順どおりなのに14バージョンも古いものが入った。
- 原因はNodeのバージョン(24未満)とnpmのインストール時のバージョン解決の仕組みにあり、エラーも警告も出ない静かな落とし穴だった。
- アクセシビリティツリーでAIエージェントがブラウザを操作する仕組み自体は、ローカルの検証用ページで実際に動かして確認できた。

---

今日取り上げたのは、Vercel LabsがGitHub Trendingに新着で挙げていたagent-browserとagent-desktopというCLIだった。スクリーンショットではなく、ブラウザやOSのアクセシビリティツリーをテキスト化してAIエージェントに渡す、という方式に興味を持ったのがきっかけだ。Playwright MCP比で約90%少ないトークン消費を主張しているという説明も、具体的な数字として確かめてみたくなった。

導入は公式READMEどおり`npm install agent-browser`を叩くだけのはずだった。ところが、入ったパッケージのバージョンを確認すると0.27.0で、npmのレジストリ上の最新版は0.41.2だった。14バージョンも差がある。しかもエラーも警告も出ていない。最初は自分のコマンドの打ち間違いかと疑い、何度か入れ直してみたが結果は同じだった。

ここで少し時間を使って原因を追った。各バージョンの`engines`フィールドを見比べると、最新の0.41.x系はNode 24以上を要求しているのに対し、古い0.27.0にはその制約が無い。さらにnpmの内部ログを`--loglevel silly`で覗くと、バージョン未指定のインストールは`agent-browser@*`という範囲指定として処理されていることが分かった。つまりnpmは、その範囲の中から現在のNode(今回は22系)の`engines`要件を満たすバージョンを選んでおり、要件を満たさない新しいバージョンは静かに除外されていた。`@latest`のように明示的に指定すればこのフィルタを経由せず最新版が入る、ということも確認できた。

この一連の調査は、最初は単なる「なぜ動かないんだ」という戸惑いだったが、仕組みを追っていくうちに、これは自分だけの問題ではなく、Node 24をまだ使っていない読者が同じ手順を踏めば誰でも再現する落とし穴だと気づいた。エラーが出ないぶん、気づかずに古いバージョンのまま使い続ける人もいるかもしれない。

本題のアクセシビリティツリーでの操作そのものは、思っていたよりすっきりと動いた。ローカルに日本語のフォームを置いたページを用意し、`open`でページを開き、`snapshot`で構造を取得し、返ってきた`@ref`を使って`fill`と`click`を呼ぶと、座標やピクセルの指定なしにフォームへの入力と送信ができた。送信後の`snapshot`にも、JavaScriptによる画面更新がきちんと反映されていた。

トークン消費量についても、同じページで素のHTMLとagent-browserのsnapshot出力を文字数で比較してみた。結果は約48.6%の削減で、公式が主張する約90%には届かなかった。比較対象や検証ページの規模が違うので単純には並べられないが、「タグやスタイル情報を削ぎ落として意味のある構造だけを残す」という方向性自体は、自分の手元の小さな実験でも確かに効いていた。

姉妹ツールのagent-desktopについては、デスクトップアプリを操作するための前提(ディスプレイやアクセシビリティバス)がこの検証環境に無く、プラットフォーム判定までしか確認できなかった。実際のGUI操作の検証はローカルPCに持ち越すことになった。

ローカルPC(Windows 11上のWSL2、WSLgというGUIセッションを持つ環境)で、持ち越した2つを確かめた。まずNodeのバージョンを22と24で切り替えて同じインストールコマンドを試すと、予想どおり22では古いバージョンが入り、24では最新版が入った。仮説が実測で裏付けられ、ここは素直に嬉しかった。

agent-desktopのほうは、思っていたより一歩だけ奥まで進んで、また別の壁にぶつかった。`accessibility.state`はクラウドでの「denied」から「granted」に変わり、WSLgでもAT-SPIのバス自体は機能していることが分かった。ところが実際にブラウザのウィンドウを操作しようとすると、「ネイティブウィンドウだと証明できない」という聞き慣れないエラーで止まった。Chromiumの起動オプションを何通りか変えても同じ結果だった。ツール自身が持っているドキュメントを読むと、Linux版はGNOMEというデスクトップ環境を前提に動作確認されているとあり、手元の環境のウィンドウマネージャを調べると、GNOMEではなくWestonという別のものだった。ここで初めて、なぜ止まるのかの輪郭がつかめた。

結局、agent-desktopのGUI操作そのものは最後まで確認できなかったが、「権限は通ったのに、その先の特定のチェックだけが、想定デスクトップ環境の違いで満たせない」という、クラウドの「そもそも何も無い」とは質の違う結果にたどり着けた。原因がはっきりしているぶん、これも今日の検証としては十分な収穫だったと思う。

ただ、この結論を出した直後に一つ気になる指摘をもらった。画面のスクリーンショットを見ると、テストページではなく接続エラーの画面が表示されていたのだ。調べてみると、ローカルのHTTPサーバーをバックグラウンドで立てた方法に不備があり、起動したコマンドの終了と同時にサーバー自体が落ちてしまっていた。ブラウザが本当にテストページを表示できているかを確かめないまま結論を出していた、ということに気づかされた瞬間だった。サーバーを正しく立て直し、今度はテストページが確かに表示されていることをスクリーンショットで確認してから、もう一度同じコマンドを実行した。結果は変わらなかった。正しいページが表示されている状態でも、同じエラーで止まる。これで結論に対する自信が一段階上がった。検証では「動いたはずだ」ではなく「本当に動いている状態を確認してから結論を出す」ことの大事さを、今日はあらためて学んだ。
