# Day 016 note原稿: diagram-designに自分のリポジトリを図解させてみた

要点:
- diagram-design(MIT)というagent skillに、自分のリポジトリCLAUDE.mdの運用フローとexperiments/day-NNNの増え方を図解させた。
- アーキテクチャ図を描く途中で、スキル自身の「常に一緒に動くノードは1つにまとめる」という原則に、自分の設計を直された。
- 公式インストールは今回もクラウド実行環境のサンドボックスに拒否され、スキルの指示書を手で読んで適用する方法を続けた。

---

## きっかけ

このシリーズでは以前(Day 011)にも diagram-design というagent skillを扱ったことがある。
そのときはスキルの「見た目」を確かめるのが目的で、自分たちのリポジトリの運用フローをスイムレーン図にし、素のMermaidと見比べた。

今回のbacklog.mdには、同じリポジトリについてもう一件メモが残っていた。
今度は見た目の比較ではなく、「このスキルに自分のリポジトリの構造そのものを説明させたら、どこまで使えるツールなのか」を確かめてみようという趣旨だった。
具体的には、CLAUDE.mdに書かれている1日の運用サイクル(朝のリサーチ→通勤中の人間→昼の実装→夜の人間レビュー)をフローチャートにすること、そして`experiments/day-NNN`というディレクトリが1日ごとに積み重なっていく構造をアーキテクチャ図にすること、の2つだった。

## 葛藤・失敗

まず公式のインストール手順を試した。
`claude plugin marketplace add cathrynlavery/diagram-design` を実行すると、今回もクラウド実行環境のサンドボックスに `[Untrusted Code Integration]` という理由で拒否された。
Day 011のときと全く同じ結果だったので、今回は時間をかけて回避策を探すことはせず、前回確立した方法——リポジトリを読み取り専用でcloneし、スキルの指示書(`SKILL.md`と各図タイプのリファレンス)を自分で読んで、その設計ルールを手で適用する——をそのまま続けることにした。

フローチャートの方は迷いなく進んだ。
CLAUDE.mdの4段階フローに、実装Routine自身が持っている「today.mdが未設定なら何もせず終了する」という分岐を組み込めば、自然にひし形の分岐ノードが1つ入る構成になった。

手が止まったのはアーキテクチャ図の方だった。
`posts/x`・`posts/note`・`posts/cards`という3つの出力をどう描くか考えていたとき、最初は素直に別々の3つのノードにするつもりだった。
ところが、改めてSKILL.mdの冒頭を読み返すと、「常に一緒に移動する2つのノードは1つのノードである」という一文があった。
考えてみれば、この3つのファイルは実装Routineが必ず同じタイミングで1セットとして作るものだ。
スキルの原則に素直に従って1つのノードにまとめてみると、ノード数は8から6に、矢印は7から5に減った。
図を描くためのスキルに、自分自身の設計判断のほうを直されるという、少し不思議な感覚だった。

## 学び・気づき

今回の検証で得られたのは、「図解ツールを使う」という行為の中に、実は「何を1つの単位として扱うか」という設計判断そのものが含まれているという気づきだった。
diagram-designのSKILL.mdは単なる配色やフォントのルールブックではなく、「何を描くべきで、何を描くべきでないか」という判断基準まで持っている。
その基準を自分のリポジトリという具体的な題材に当ててみて初めて、原則が机上の空論ではなく実際に効く場面があることが分かった。

ブラウザでの表示確認についても、今回は収穫があった。
Day 012の検証時点ではこのクラウド実行環境にブラウザが入っておらず、見た目の確認はHTMLの目視チェックにとどめていた。
今回は環境にChromiumがプリインストールされていて、Playwright経由で実際に2枚の図とシェアカードを開き、consoleエラーが出ていないことまで確認できた。
同じ「Routine環境の制約」でも、何が使えて何が使えないかは日によって変わりうる、ということも分かった一日だった。
