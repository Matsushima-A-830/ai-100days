## 要点(3行)

- Grok Botの代わりに、手元のClaude Code CLIをそのままバックエンドにできるOSSチャットアプリ「OpenMausBot」を動かしてみた。
- 新しいAPIキーは一切追加せず、既存のログインをそのまま検出・実行できた。
- 「危険操作は確認カードが出る」という説明が、CLIだけでなく実際にGUIを開いて確かめても当てはまらず、原因もCLI/GUIの違いとは別のところにあった。

---

GitHub Trendingで見かけたOpenMausBotの紹介文を読んで、最初に引っかかったのは「xAIのGrok Botへのアンチテーゼ」という立ち位置だった。
Grok Botはクローズドソースで、使えるモデルもxAI系に固定されている。
OpenMausBotはその逆で、自分のPCやサーバーに既にログイン済みのclaude・codex・grokといったCLIを、そのままチャットのバックエンドとして使う設計になっている。

筆者はふだんClaude Code CLIで検証作業をしている。
だったら、このCLI自身を別のOSSチャットアプリに差し込んで動かせるのか、自分で確かめてみようと思った。

最初の小さな引っかかりはNodeのバージョンだった。
`npm view`で確認すると`engines`に`node >=24`と書かれていて、手元の環境のデフォルトNodeはそれより古かった。
幸い別途Node 24系が用意されていたので、そちらに切り替えて進めることができた。
この手の前提条件の食い違いは、実際に手を動かしてみるまでなかなか気づけない。

インストールとサーバー起動は拍子抜けするほど素直に進んだ。
GUIを一切開かず、`serve --no-open --local`だけでサーバーが立ち上がり、`doctor`コマンドを叩くと`Engines available: claude`という表示が返ってきた。
新しい設定ファイルも、新しいAPIキーも何も追加していないのに、既にこの環境にログインしていたClaude Code CLIをそのまま認識していた。
これは正直、気持ちのいい瞬間だった。

次にやったのは、実際にタスクを投げてみることだった。
ファイルを1つ作らせ、できたファイルを`cat`して内容が一致することを確認した。
次に、別に用意したファイルをシェルコマンドで削除させてみた。
ここで想定していたのは、事前に読んでいた説明通り「危険な操作には許可/拒否カードで確認が入る」という挙動だった。

ところが、確認は一切出なかった。
`rm`の指示を送った瞬間にファイルは消えていた。
起動ログを読み返すと`local requests: owner trust (self-hosted default)`という一行があり、セルフホストでオーナー本人として使う今回の構成では、確認フローそのものが働かないという設計だったことが分かった。
説明を読んだだけでは分からず、実際に手を動かして初めて気づいた挙動だった。
理屈としては「自分のCLIをオーナーとして動かしているのだから当然」と理解できる一方、ドキュメントの文面からの印象とは少しずれていた。

ここで一度区切りがついたのだが、実際にGUIを開いて確かめてほしいという宿題が残った。
ローカルのPCでブラウザUIを開き、ペアリングコードでオーナーとして入り、同じ依頼を今度はチャット欄から直接送ってみた。
結果は同じだった。
GUIでも確認は出ず、即座に実行されようとした。

ここで最初の理解が間違っていたことに気づいた。
`owner trust`という起動ログの一文のせいで「CLIで動かしているから確認が省略される」のだと思い込んでいたが、実際にはそうではなかった。
botの設定画面を開くと、「Before MausBot acts」という項目が最初から「Just do it」になっていた。
CLIかGUIかではなく、新しく作ったbot自体が、最初から確認なしで動くように設定されていたのだった。

では設定を「Ask me first」に変えればカードが出るはずだ、と思って切り替えて同じ依頼を送った。
今度は確認カードの代わりに、エラーで処理が止まった。
詳細を開くと「必要なMCPツールが見つからない」という内容で、確認カードを出す仕組み自体が、今回のセットアップでは機能していないことが分かった。
2回試して、どちらも同じ結果だった。

もう一つ、別の発見もあった。
作業ディレクトリの外側にファイルを作らせようとすると、今度は明示的に「権限がない」と断られた。
確認カードとは別に、botのシェルは専用の作業フォルダに閉じ込められているという、もう一つの安全装置が効いていたということになる。

今回の検証を通じて学んだのは、ツールの説明文が描く挙動と、実際に自分の手元で再現した挙動は、思っていたよりずれることがあるという当たり前の事実だった。
しかも、最初に立てた仮説(CLIだから確認が省略される)も、実際にGUIまで確かめてようやく違うと分かった。
Grok Botへのアンチテーゼとしての設計思想そのものには納得感があるし、既存のCLIログインをそのまま流用できる手軽さは素直に便利だと感じた。
一方で、「確認カードで危険操作から守られている」という前提は鵜呑みにせず、自分の手で実際にカードが出るかどうかを確かめる必要がある、ということを今回は強く実感した。
