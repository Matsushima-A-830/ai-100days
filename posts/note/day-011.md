# 指示書を実行できなかったので、指示書を自分で読むことにした

## きっかけ

今日のネタは、GitHub Trendingで全言語2位まで急伸していた diagram-design というプロジェクトだった。
Claude Codeに追加するagent skillで、「自然言語の指示だけでエディトリアル調の図解を自動生成する」とREADMEにある。
素朴なMermaid風の図ではなく、雑誌の誌面みたいな見た目の図がぽんと出てくるらしい。
これは面白そうだと思って、公式の手順通りに試すつもりだった。

```
/plugin marketplace add cathrynlavery/diagram-design
/plugin install diagram-design@diagram-design
```

## 葛藤・失敗

このコマンドを実行した瞬間、環境の自動パーミッション分類器に拒否された。
理由は「Untrusted Code Integration」。
今回のクラウド実行環境は、外部のplugin marketplaceを無条件には追加させてくれない作りになっているようだった。

ならばとリポジトリだけをread-onlyでcloneして、同梱されているチェック用のPythonスクリプトを直接実行しようとしたが、こちらも「Code from External」という理由で拒否された。
ここで一瞬、今日のネタはこのまま検証できずに終わるかもしれないと思った。

ただ、拒否された理由はどちらも環境の安全策として筋が通っていて、無理に回避する類のものではないとすぐに判断がついた。
ではどうするか、と考えて手が止まった時間が、今日の作業の中で一番長かった。

## 学び・気づき

落ち着いて `SKILL.md` を読み直してみると、このスキルの正体は実行可能なプログラムではなく、色のトークンや余白のグリッド、矢印のラベルの置き方まで細かく書かれた「指示書」だということに気づいた。
plugin機構は、この指示書をエージェントに読ませて実行させるための配布経路でしかない。
配布経路が使えないなら、指示書を自分で読んで、自分の手でそのとおりに図を組み立てれば、スキルが本来やろうとしていることの価値そのものは確かめられるはずだと考えた。

そこで、このリポジトリ自身の1日の運用フロー(朝のRoutineが候補を集めて、通勤中に自分がマージして、昼のRoutineが検証して、夜に自分がレビューして公開する、という流れ)を題材に、指示書どおりにHTML+インラインSVGのスイムレーン図を組み立てた。
比較のために、同じ内容を素のMermaidでも描いてみた。

結果を並べてみると、見た目の差は思っていたよりはっきりしていた。
Mermaid版は良くも悪くも「いつものMermaidの見た目」で、diagram-design版は一貫したデザインのルールに沿った図になっていた。
さらに手でチェックリストを当てていく中で、スキル自身が配っているサンプルHTMLが、スキル自身のチェックリストの一項目(SVGをスクロール可能なラッパーで囲む、という要件)を満たしていないことにも気づけた。
これは、plugin経由で一発インストールして試しただけでは見落としていたかもしれない発見だった。

検証方法を変えざるを得なかったのは想定外だったが、おかげで「このスキルは何でできているのか」という、本来なら読み飛ばしていたかもしれない部分までちゃんと読むことになった。
遠回りをしたぶん、得たものは多かった日だった。

## 追記: ブロックされていたことを、後日実際に試せた

記事を公開する前に、当時ブロックされて試せなかった公式インストールを、クラウド環境とは別のローカルPCで試してみた。結果はあっさり成功した。plugin marketplaceの追加もインストールも、特に何の問題もなく通った。

せっかくなので、同梱されていた自動チェックスクリプトも実際に動かしてみた。手作業で組み立てた自分の図は、このチェックにもちゃんと合格した。一方で、以前見つけたサンプルHTMLの小さな不整合(スクロール可能なラッパーの件)は、この自動チェックでは引っかからないこともわかった。つまりあの発見は、人間やエージェントが目で見て確認する前提のチェックリストにしか載っていない項目で、自動化されたチェックの範囲外だったということになる。

回り道の末に自分の手で組み立てた図が、最終的に公式のチェックにも通ったという結果を見て、遠回りした価値がもう一段深まった気がした。
