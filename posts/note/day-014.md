# Day 014 note原稿

要点3行:
- TokenRouter(複数LLMをトークン単位でルーティングする推論サーバー)はライセンスが未確定で、記事の主役にはできなかった。
- 検証の途中で踏んだ「最新GPU(Blackwell)だと動かない」という別の壁は、依存ライブラリの差し替えと、残ったAPIの食い違いへの小さなソースパッチで越えられた。
- エラーメッセージを読んで終わらせず、どのバージョンのどの関数が問題なのかを1つずつ切り分けていった過程が、今回一番書きたかったことだった。

---

14日目に選んだTokenRouterは、Hugging Face Daily Papersに載っていた、複数のLLMをトークン単位で振り分けて推論コストを抑えるという手法だった。検証に着手する前にいつものようにライセンスを確認したところ、リポジトリにLICENSEファイルが同梱されておらず、`pyproject.toml`の分類タグに「Apache」とあるだけで確定情報が無かった。これまでのルール通り、ライセンスが不明なツールのコードや検証結果を記事の主役にすることは避けることにした。

ここで「じゃあ今日は書くことが無い」で終わってもおかしくなかった。ただ、検証を進める過程で、TokenRouter自体とは別の、もう一段下の層の問題にぶつかっていた。クラウドの実行環境にはそもそもGPUが無く、ローカルPCにエスカレーションしたところ、今度はGPU自体はあるのに「RMSNorm failed with error code no kernel image is available for execution on the device」という聞き慣れないエラーで推論サーバーがクラッシュした。

最初は「GPUがあるのにGPUが無いと言われる」ような不思議な状況に見えた。調べていくと、原因は自分のGPU(発売されたばかりのBlackwell世代)に対して、推論サーバーが依存しているCUDAカーネルの実装ライブラリの事前コンパイル済みバイナリが、まだそのGPU世代向けのコードを含んでいなかったという話だった。torch自体は新しいGPUをちゃんと認識できていたので、「GPUが無い」から「ライブラリのビルドが新しいGPU世代に追いついていない」へと、問題の輪郭が変わった瞬間だった。

ここから意地になって、依存ライブラリの新しいバージョンを1つずつ試す作業に入った。幸い途中のバージョンまではtorchとの互換性を保ちながら、新しいGPU世代向けのコードが追加されていることが分かり、問題のカーネルを単体で呼び出すテストでは実際に動いた。ところが、本体の推論サーバーを起動しようとすると、今度は別のImportErrorで止まった。ライブラリ側の関数名がバージョン間で変わっていて、サーバー側がまだ古い名前を前提にしていたのだ。

一見するとまた振り出しに戻ったようだったが、よく見ると、無くなった関数が実際に呼ばれているのは、特定の量子化手法を使うときだけの、2箇所のコードパスだけだった。自分が動かしたいモデルはその量子化を使わないので、importを少し先延ばしにする(失敗したらNoneにしておく)だけの小さな変更で十分だと分かった。実際にその変更を入れて再起動したところ、以前クラッシュしていた最初の推論リクエストを無事に通過し、きちんとテキストが生成された。

今回いちばん印象に残ったのは、「ライセンスが分からないから記事にできない」という制約に当たっても、その周りで実際に手を動かしていれば、別の書けることが見つかるという感覚だった。エラーメッセージ1つで「対応していないので無理」と判断するのではなく、どのバージョンのどの関数が問題なのかを1段ずつ掘っていくと、思っていたより小さな変更で越えられる壁もある。最新のGPUを使っていると、今後もこの種の「ライブラリがまだ追いついていない」という壁には当たりそうだが、今回のやり方は次に同じような状況に出会ったときの引き出しになりそうだ。
