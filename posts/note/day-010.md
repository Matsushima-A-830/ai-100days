# Day 010 note原稿: 「何でもリバースエンジニアリングしてくれる」の中身を自分で試してみた

**要点3行**
- GitHub Trendingで急伸していたMCPサーバー「REA」を、自分で書いた小さなElectronアプリ(割引ロジック+隠しデバッグ機能つき)で検証した。
- アプリの構造(IPC配線・公開API)の再構築は完全に正確だったが、「なぜそれが隠し機能か」の説明は自動では出ず、自分でEvidenceを読む一手が必要だった。
- 「Reverse Engineer Anything」という名前は、「ツールが説明してくれる」ではなく「説明に必要な事実を揃えてくれる」という意味だと理解するのが実態に近い、という発見があった。

---

## きっかけ

GitHub Trendingで一日に4,000スター以上増えていた「REA」というリポジトリを見つけた。コーディングエージェントにネイティブバイナリやElectronアプリを解析させ、「元のソースを復元しない前提で機能の挙動を調べる」ためのMCPサーバーだという。README には「See a feature you like. Understand how it works, down to the binary level.」と書かれていて、見た目のインパクトは強い。

ただ、backlog.mdに候補として積んだ時点では「スター数が伸びているからすごい」以上のことは何も確かめていなかった。本チャレンジのルールは「動かしていないものを動いたと書かない」なので、まず自分の手で動かしてみることにした。

## 葛藤・失敗

最初に迷ったのは検証対象だった。REAは第三者のアプリを解析するためのツールだが、著作権・利用規約の問題を避けるため、今回は自分で小さなElectronアプリを書いて、それを解析対象にすることにした。せっかくなので「正解を自分だけが知っている」状態を作ろうと思い、クーポンコードの文字コードを使った少し込み入った割引ロジックと、特定の環境変数のときだけ有効になる隠しデバッグ機能を仕込んだ。

次に迷ったのは、REAをこのクラウド実行環境の「エージェント」として正式に登録するかどうかだった。README通りに`rea setup`を実行すればMCPサーバーとして接続できるが、これはこのセッション自体のグローバルな設定ファイルを書き換える操作で、検証の目的に対してリスクが見合わない。幸い、REA自身のドキュメントに「CLIを直接呼び出せば、MCP登録もHopper/Ghidraも無しで同じEvidenceが返る」という正式なフォールバックが明記されていたので、そちらを使うことにした。

一番つまずいたのは、機能追跡用のコマンド(`trace_application_feature`)の入力形式だった。`--help`を見ても`--schema`を見ても、肝心のJSONの内部構造(キー名や許される値)が書かれていない。GitHub上のガイドにも「IPCチャンネル名などを渡せる」という説明はあっても、JSONのキー名までは載っていなかった。

試しに空のJSONを渡してみると、バリデーションエラーがどのキーが足りないかを教えてくれた。そのエラーメッセージを手がかりに、もう一段階深く空のオブジェクトを渡してみると、今度は`seed.kind`に許される値(文字列・ノードID・IPCチャンネルなど)まで出てきた。結果的に、ドキュメントを読むよりもエラーメッセージを読む方が正確な答えに近づけた。

さらに期待外れだったのは、識別子の名前(関数名やプロパティ名)をそのままこの追跡機能に渡しても、何も見つからなかったことだ。IPCチャンネル名のような文字列リテラルなら正確に追跡できるのに、変数名や関数名では「一致なし」になる。「何でも検索できる」わけではなく、何を渡せば見つかるかというルールが明確に存在していた。

## 学び・気づき

一番の収穫は、「アプリの構造を正確に再構築する」ことと「機能の意味を説明する」ことが、REAの中では別の層になっているとわかったことだった。IPCチャンネルの数やcontextBridgeで公開されているAPIの数は、1回の解析で数値としてすべて正解と一致した。隠しデバッグ機能のトリガーになる環境変数の読み取りも、最初の解析結果の中にすでに記録されていた。

ただ、「この環境変数がこの値のときだけ隠し機能が有効になる」という1文の説明は、どのコマンドを叩いても自動では出てこなかった。返ってきた構造化データ(Evidence)を自分で読んで、関数の呼び出し関係をたどって初めて、その説明にたどり着けた。

「Reverse Engineer Anything」という名前から、最初は「どんなアプリでも機能を解説してくれる」という印象を持っていたが、実際に動かしてみると、REAがやっているのは「正確な断片的事実を漏れなく揃えること」で、それらを繋いで意味のある説明にする作業は、今のところエージェント(あるいは人間)の仕事として残っている。今回は変数名を短くしただけの軽い難読化だったので、人間が直接ソースを読んでも正解に着地できたが、もっと大規模で本当に難読化されたアプリだったら、この「事実を揃える」工程そのものに価値が出てくるのだろうと感じた。

派手な宣伝文句をそのまま信じるのではなく、小さくても自分で確かめられる範囲を作って動かしてみることで、ツールの本当の強みと限界の輪郭が見えてくる。今回はそれを実感できた一日だった。
