# Day 025 X投稿案: AKV (Cache Engineering for Agents)

## パターンA: 要点訴求型

```
エージェントの履歴圧縮は「要約」じゃなくて「KVキャッシュを直接操作」でもいいらしい(清華大/HF Daily Papers 4位の論文)。

135Mモデルで自分で再実装して試したら、素朴にキャッシュを削るだけだと品質が悪化(loss 0.80→1.49)。でもRoPEの回転を付け替える"repos"操作を足すとほぼ元の品質に戻った(0.84)。しかもコストは要約の再prefillの1/30。

https://huggingface.co/papers/2610.28577
```

## パターンB: 驚き訴求型

```
KVキャッシュの位置エンコーディングって、実は「足し算」できる。

R(a)×R(b)=R(a+b)というRoPEの合成則を使えば、キャッシュ済みのKeyに回転を追加で乗せるだけで「位置をずらしたKey」に変換できる。逆回転して作り直す必要すら無い。この性質を使ってAKV論文の"repos"操作を自分で実装し、135Mモデルで動かしてみた。

https://github.com/thu-nics/AKV
```

## パターンC: 技術者向け詳細型

```
AKV(Cache Engineering for Agents, HF Daily Papers 2026-10-22 4位)の"drop"/"repos"操作を、公式コード不使用でSmolLM2-135M-Instruct(CPU)に自前実装して比較した。

架空の棚卸しエージェント会話(tool応答4回)で、古い2応答のKVを:
・drop(位置補正なし): final cache 223tok, loss 1.4868(悪化)
・drop+repos(RoPE追加回転で位置を付け替え): final cache 223tok, loss 0.8386(full=0.8047に近い)
・summarize(要約+全体再prefill): final cache 257tok, management 180.86ms
・drop+reposのmanagement操作は6.13ms(要約の約1/30)

ただし自由生成では135Mモデルがどの方式でも正解(14台)を出せなかった点は正直に明記。
詳細: experiments/day-025/
https://huggingface.co/papers/2610.28577
```
