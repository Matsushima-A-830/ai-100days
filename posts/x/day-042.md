## パターンA: 要点訴求型

Claude Code CLIを文脈圧縮プロキシ`billion-context`でラップして検証。

- `bili claude` でそのままラップ成功、MCPツール(acp_status/compress等)も注入確認
- 6ターンの小規模テストで実際に自動圧縮が発動: 17,242トークン→299トークン(約98%減)
- ただし圧縮はキャッシュを壊し、そのターン単体のコストは直接呼び出しより高くついた
- ローカルPCで追試: npm install -gは問題なく成功、圧縮後も記憶は正確(1488を正しく再回答)

## パターンB: 驚き訴求型

「17,242トークンの会話を299トークンに圧縮」——これは本当に起きた。

でも同じターンで、プロンプトキャッシュの再構築コストが2倍に跳ね上がって、結局そのターンの支払いは直接呼び出しより高くなった。

圧縮は確かに動く。ただ「縮んだ分を何度も安く読み返す」フェーズまで、6ターンの検証では到達できなかった。

気になって、ローカルPCで圧縮後にもう一度同じ質問をしてみた。299トークンの要約の中に、最初の質問への回答そのものが折り畳まれていたが、答えは変わらず正しかった。圧縮は記憶を壊さない、らしい。

ranxianglei/billion-context、Claude Code CLIを自己言及的に検証した結果。

## パターンC: 技術者向け詳細型

billion-context(ranxianglei, MIT)を`bili claude`経由でClaude Code CLIにMITMプロキシとして挟んで検証。

ターン1-4: cache_read_input_tokensは直接呼び出しとほぼ同ペースで増加(MCPツール定義注入分だけ+4%のオーバーヘッド)。

ターン6: context 225813 tok が preflight target 200000 を超え、自動で「preflight overflow compress」発動。m00008-m00011(17,242 tok)を299 tokへ圧縮。

同ターンのcache_creation_input_tokensは17,957→36,642に跳ね上がり(直接系は変化なし)、cache_read自体は115,866→80,448に減少。

おまけ: biliのログは claude-sonnet-5-5 の model window を200,000としていたが、Claude Code CLI側のusage.modelUsageは contextWindow:1000000 を報告。内部モデルレジストリの食い違いの可能性あり。

ローカル追試: npm install -g は通常環境では成功(Routine環境固有の制約と確認)。同じBefore/Afterパターン・圧縮の自動発動も別環境・claude-sonnet-5-5指定で再現。圧縮ブロック(18.9K→303 tok、"LOG-00001 lookup"含む)が生成された後に同じ質問をしても正しく1488と回答し、圧縮後の記憶の正確性を確認できた。
