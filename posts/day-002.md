## X投稿案

### パターン1: 要点訴求型

Googleがgiflib(CのGIFライブラリ)をGeminiでRustに書き換えて差分ファジングした事例を、規模を縮小して自分の手元で再現した。

境界チェック漏れのあるC実装 → AIでRustに書き換え → 悪意ある入力1000件近くで挙動比較。C版はASan無しだと検出されずに静かに壊れ、Rust版は最初からクラッシュしない。

出典: https://bughunters.google.com/blog/scaling-memory-safety

### パターン2: 驚き訴求型

一番怖かったのは、ASanを付けずに動かしたC版が「out_cap=4なのに20バイト書き込んでも」クラッシュせず正常終了(exit 0)したこと。

ヒープは確実に壊れているのに、見た目上は「動いている」。ASanを付けて初めてheap-buffer-overflowとして検出された。Rust版は最初からその書き込みが起きない。

出典: https://bughunters.google.com/blog/scaling-memory-safety

### パターン3: 技術者向け詳細型

giflibのRust移行事例(Gemini使用、出典: https://bughunters.google.com/blog/scaling-memory-safety)を、CWE-787クラスのバグ(サイズチェック漏れによるヒープ書き込み)だけ抜き出したミニRLEデコーダで再現。

- C版: out_capのチェック無しでout[out_pos]に書き込み
- Rust版: out.len() >= out_capでEarly return Err、書き込み自体が起きない
- 正常系1000件をrandom.Random(42)固定シードで生成しC/Rustの出力バイト列を比較 → mismatches=0
- 異常系(out_cap超過): gcc -fsanitize=addressでheap-buffer-overflow検出、Rust版はパニング無しでErr

補足: clangのASanランタイムがコンテナに無くビルド失敗、gccのASanに切り替えて回避(この詰まりも記事に書いた)。

## note原稿

**要点3行**
- GoogleがGeminiでgiflib(C)をRustに書き換えた事例を、個人が6時間で再現できる規模に縮小して実際にやってみた。
- 境界チェック漏れのあるCコードは、ASan無しでは「クラッシュせず静かにヒープを壊す」のが一番怖い。AIが書き換えたRust版は同じ入力で最初からクラッシュしない。
- 正常系1000件の出力比較(差分ファジングの簡易版)は完全一致。挙動を変えずに安全性だけ追加できたことを確認できた。

---

giflibという、GIF画像を読み込むための古いCライブラリがある。Googleが最近、これをAI(Gemini)の力を借りてRustに書き換えたという記事を出していて(出典: https://bughunters.google.com/blog/scaling-memory-safety)、なかでも「移行のおかげで公開前だったゼロデイの影響を受けなかった」という一文がとても印象に残った。

とはいえgiflib本体は3,000行あって、個人がその日のうちに丸ごと再現するのは無理がある。そこで「giflibで実際に問題になっていたバグのクラス」だけを抜き出して、自分で最小限のC実装を書き、それをAI支援でRustに書き換える、というミニ実験にスコープを縮小してみた。

やったことは大きく3つ。

1. サイズチェックを一切していない、危険なC版のRLE(Run-Length Encoding)デコーダを書く
2. 同じ挙動を持ちつつ、容量を超えたら安全にエラーを返すRust版を書く(ここはClaude Codeに書いてもらった)
3. 正常な入力での出力一致と、悪意ある入力での挙動差を、実際にコマンドを実行して比較する

一番印象的だったのは、C版をASan(AddressSanitizer)なしでビルドして悪意ある入力を投げたときの結果。4バイトしか確保していないバッファに20バイト書き込んでいるのに、プログラムはクラッシュせず`exit code 0`で終わった。ヒープは確実に壊れているのに、見た目上は何も起きていないように見える。これがまさに「メモリ安全バグが怖い」と言われる理由そのものだと実感した。ASanを付けて同じ入力を投げると、今度はきちんと`heap-buffer-overflow`として検出され、バグのある行までピンポイントで教えてくれた。

一方Rust版は、そもそも容量を超える書き込みが発生する前に`Err`を返す実装にしたので、同じ入力でもクラッシュもパニックもせず、ただエラーメッセージを出して終了した。

最後に、ランダムに生成した「正常な」入力1000パターンについて、C版とRust版の出力バイト列が完全に一致するかをPythonスクリプトで確認した。結果はmismatches=0。挙動を変えずに安全性だけを追加できていることを、簡易的にではあるが確認できた。

途中、clang用のASanランタイムがこの検証環境に入っておらずビルドに失敗する、という小さな詰まりもあった(gccのASanに切り替えて回避)。この手のつまづきもそのまま記事に残している。
