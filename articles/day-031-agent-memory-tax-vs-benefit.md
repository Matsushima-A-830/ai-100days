## 今日のネタ元

Hugging Face Daily Papersに掲載されていた以下の論文を検証した。

- "Memory Tax: Dissecting the Net Value of Agent Memory"
- https://huggingface.co/papers/2610.34073 (arXiv:2610.34073)

この論文は、フラット型・階層型・グラフ型・学習済みポリシー型という10種類のエージェント
メモリシステムを、会話履歴に直接検索をかける素朴なRAGと比較している。
結論は刺激的で、多くのメモリシステムがRAGの素のスコアを下回ると報告しているのである。
論文はこの現象を「メモリがRAGの取りこぼしに答えられる利益(benefit)」と「RAGが答えられる
設問にメモリの方がむしろ誤答する税(tax)」に分解し、税が起きる原因を構築時の忠実性・
検索のしやすさ・バックボーン変更への頑健性という3つの観点で分析している。

本チャレンジではDay 028で近い論点(変異型メモリ vs 追記のみメモリ vs 素朴なRaw-RAG)を
扱ったが、この論文の「利益と税に分解する」という切り口は新しく、特に「メモリが要約の過程で
捨てた細部を、素朴な検索はキーワードが合えば拾ってしまう」という説明に興味を持った。

## 検証の方針と制約

著者独自実装のコードは、Hugging Face PapersのページとarXivページのどちらにも見当たらな
かった。
フル再現にはLongMemEval-s・PersonaMem-v2・MINT-Evalといった大型ベンチマークと、Qwen3.5-4B
などの複数バックボーンが前提になっており、本チャレンジの「6時間以内に検証できるものを選ぶ」
「有料APIキーが必須の候補は選ばない」という方針には合わない。
そこで、論文の「利益 vs 税」という分解の考え方だけを借りて、自作の小規模な会話ログで
縮小版の概念実証を組むことにした。
追加のAPIキー・GPUは一切使っておらず、Claude Code自身を解答モデルとして使っている。

## 作ったもの

架空の多セッション会話ログを2本書き起こした。

1. 社内ダッシュボード再設計プロジェクトの計画会議(3セッション・37ターン)。
   技術スタック(React→Svelte)・予算(12万→15万→14万ドル)・締め切り(Q2末→Q3末→7月15日)・
   チーム構成(4人→6人→5人)が会話の進行とともに変化していく。
2. 家族旅行の計画(3セッション・34ターン)。
   行き先(ポルトガル→スペイン)・人数(4人→3人)・予算(4000→4800→4200ドル)・ホテルが
   変化していく。

どちらにも、一度しか言及されない具体的な事実を意図的に埋め込んだ。
ステージングサーバーの機種(Dell R710)、クライアントとのデモの日時・場所、レンタカーの
確認番号、食物アレルギーといった情報である。

この同じ会話ログに対して、2つの「答え方」を実装し、同じ16問(2会話×8問)に答えさせた。

1. **RAG条件**: 会話ログ全文に対して、形態素解析器を使わない素朴な文字bigramのTF-IDF検索
   (外部ライブラリ不使用の自作スクリプト)でtop-5ターンを取得し、その5件だけを見て答える。
2. **メモリ条件**: 「現在値は上書きし、明示的に議論された主要な意思決定(技術スタック・
   予算・締め切り・チーム構成など)は変更履歴として残すが、議論の対象にならなかった付随的な
   細部は現在値のみ残して過去を捨てる」という典型的な要約メモリの方針で事前に構築した要約
   だけを見て答える。

正解はこの検索・要約のどちらよりも先に確定させ、解答もどちらの条件も与えられた情報だけを
見て答えた(他方の条件の情報は見ない)。
質問は「最新の値を聞くもの(current)」「既に上書きされた過去の値を聞くもの(historical)」
「複数ターンに分散した情報を集約する必要があるもの(synthesis)」「一度しか言及されない
事実を聞くもの(niche)」の4種類に分けている。

## 実行結果

検索スクリプトの実行ログ、要約メモリの内容、16問全ての解答過程と採点は、すべて
`experiments/day-031/` にそのまま残した。

結果は以下の通りだった。

| 条件 | 正答数 | 正答率 |
|---|---|---|
| RAG(素朴な検索) | 13/16 | 81.25% |
| メモリ(要約+変更履歴) | 15/16 | 93.75% |

「税」(RAGは正答、メモリは誤答)が起きたのは1件だけだった。
社内プロジェクトのステージングサーバーについて「AWSに移行する前は何を使っていたか」と
聞く設問である。
正解は「Dell R710」という古いサーバーだが、これは計画会議の中で明示的な意思決定として
扱われなかったため、メモリの要約では現在値(AWS)だけが残り、移行前の情報自体が消えていた。
一方で素朴な検索は「もうDell R710は使っていない」という一言を拾えたため、正しく答えられた。
これは論文が指摘する「構築時の忠実性」の問題、つまり要約が重要でないと判断して捨てた細部を、
素朴な全文検索はキーワードが合えば拾ってしまう、という構図をそのまま再現している。

逆に「利益」(メモリは正答、RAGは誤答)は3件起きた。
いずれも素朴な検索のtop-5に、必要な人名や複数セッションに分散した数値が十分に拾われな
かったことが原因だった。
例えば「セッション2で加わったが最終的なチームに残っていない人物は誰か」という設問では、
検索結果の5件に人名を含むターンが一件も入らず、RAGは答えられなかった。
メモリは最初から構造化された「現在のチーム構成」を保持していたため、正しく答えられた。

全体としては、税1件に対して利益3件で、今回の縮小実験ではメモリ側の正答率がRAGを上回る
結果になった。
論文の見出しである「メモリは素朴なRAGに負けることが多い」はこの縮小実験では再現しなかった。
精度が同等以上だったことを、ここで正直に記録しておく。

ただし理由ははっきりしている。
今回作ったメモリは、論文が比較している10種類の複雑なメモリアーキテクチャに比べてかなり
単純で、「現在値+明示的な意思決定の変更履歴だけを保持する」という素直な設計だった。
論文が指摘する税は、抽出・再構成・グラフ化といった複雑な構築処理を経るメモリシステムほど
起きやすいと考えられる。
また検索側も密検索やクロスエンコーダ再ランキングを実装しておらず、文字bigramのTF-IDFのみ
だったため、論文が報告するRAG-Hybridの約70%というスコアよりも検索精度が不安定だった
可能性がある(実際に3件の「利益」ケースすべてで検索の取りこぼしが観測された)。

## 筆者の所感

縮小実験とはいえ、「要約メモリがトリビア的な細部を静かに捨て、素朴な全文検索はキーワードが
合えばそれを拾ってしまう」という「税」の構図を、具体的な1例として自分の手で再現できたのは
収穫だった。
同時に、同じ素朴な検索でも、質問の表現と会話ログの表現の重なり方次第でtop-5の精度がかなり
ばらつくことも実感した。
Project Novaの予算変遷(3セッション分の金額)は検索で全て拾えたのに、家族旅行の予算変遷は
1つしか拾えなかった、という差は、検索対象の会話の中身次第で結果が変わる素朴な検索の
脆さをよく表していると思う。
「メモリは本当にRAGより劣るのか」という問いに単純な答えはなく、メモリの実装の複雑さと
検索の実装の質、両方に左右される、という当たり前だが実感しづらい事実を、小さい実験からでも
確認できた。

## 限界(正直に書く)

- 自作の2会話・16問のみで、統計的な有意性は主張できない。
- 検索器は文字bigramのTF-IDFのみで、密検索・クロスエンコーダ再ランキングは実装していない。
- メモリの要約方針を決めたのも、RAG条件・メモリ条件のどちらで解答したのもClaude自身であり、
  本物の独立したメモリシステムの実装や、別々のLLM呼び出しによる厳密な条件分離ではない。
- 論文が検証した具体的な10種のメモリアーキテクチャやQwen3.5-4B等のバックボーンは使っていない。

詳細な実行ログ・解答過程・採点はすべて`experiments/day-031/`に記録してある。
