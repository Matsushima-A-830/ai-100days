本記事は「海外で話題のAI関連ニュース/OSSを毎日検証する」100日チャレンジのDay 035。この連載自体もClaude Code Routines(クラウド上の自動実行)で運用しているが、今回検証した[Claude Code Game Studios](https://github.com/Donchitos/Claude-Code-Game-Studios)(以下CCGS、MIT License)は、Claude Codeの1セッションを49体のサブエージェント・74個のスラッシュコマンド形式スキルからなる「ゲーム開発スタジオ」として動かすテンプレートで、本日GitHub Trendingで見かけて気になった。筆者がこの連載をClaude Codeで回しているのと似た発想のツールを、実際に動かして確かめてみる。

## まず数字を数えて検証した

READMEは「49 agents・74 skills・15 hooks・14 rules・62 templates」という構成を謳っている。話を進める前に、実物のファイル数をそのまま数えて照合した。

```bash
$ ls .claude/agents | wc -l
49
$ ls .claude/skills | wc -l
74
$ ls .claude/rules | wc -l
14
```

agentsとrulesは完全一致。skillsもディレクトリ数(=スラッシュコマンド数)で一致した。hooksは`.claude/hooks/*.sh`が18個あったが、実際に`.claude/settings.json`の`hooks`ブロックに登録されているのは15個で、残り3つは登録済みフックから呼び出される共有ヘルパーだった。templatesは63個あり、READMEの62件表記とは1件ずれていたが、実害のない軽微な食い違いだった。総じてREADMEの主張はほぼ正確だった。

## クラウド実行環境では動かせなかった

朝のRoutine(クラウド上の自動実行)で、クローンしたテンプレート自身のコード(`.claude/hooks/*.sh`の直接実行や、ネストしたClaude Codeセッションの起動)を実行しようとしたところ、実行環境側の安全策である自動モード分類器に一貫してブロックされた。

```
Permission for this action was denied by the Claude Code auto mode classifier.
Reason: [Code from External]. ...
```

これはCCGS自体の不具合ではなく、自動実行されるクラウドセッションに対する安全策というRoutine環境固有の制約だったため、`/start`から`/dev-story`までの実際のワークフロー検証は、手元のPCでのローカル検証にエスカレーションした。本記事の本題はこのローカル検証の結果になる。

## 代わりに見つけた、Claude Code自体のおもしろい挙動

テンプレート自身を動かすのは断念したが、その調査の途中で意図せず別の発見があった。

テンプレートをクローンして、作業ディレクトリをそのクローン先に移した直後、こちらから何も読み込み操作をしていないにもかかわらず、このセッション自身に「クローンしたテンプレートの`CLAUDE.md`の内容」がそのまま指示として差し込まれた。しかもそれだけでなく、その`CLAUDE.md`の中で`@`記法によって参照されている4つのファイル(ディレクトリ構成の説明、エンジンのバージョン表、エージェント間の協調ルール、コーディング規約)の内容まで、連鎖的に読み込まれていた。

これが幻覚ではなく実在の機能であることは、`claude --help`で確認できた。`--bare`フラグの説明に、次のように明記されている。

```
--bare    Minimal mode: skip hooks ..., LSP, plugin sync, attribution,
          auto-memory, background prefetches, keychain reads, and
          CLAUDE.md auto-discovery.
```

"CLAUDE.md auto-discovery"というのが、まさに今回観測した挙動の名前だった。作業ディレクトリが`CLAUDE.md`を持つフォルダに入ると、セッションはその内容(と`@`で参照された先)を自動的に自分の指示として取り込む。

ここで引っかかったのは、クローンしてきたテンプレートの`CLAUDE.md`自身が、次のような「協調プロトコル」を定めていたことだ。

> Agents MUST ask "May I write this to [filepath]?" before using Write/Edit tools
> No commits without user instruction

つまり、人間がこのテンプレートを直接自分のプロジェクトとして使うことを前提にしたルールだ。今回のように「検証のために一時的にクローンして内部を調べる」だけの作業でも、cdして中に入った瞬間、このルールがそのままセッションの指示として読み込まれる。このリポジトリ自身の`CLAUDE.md`が定める運用ルール(ブランチ+PR、公開判断は人間が行う等)と、クローン先テンプレートの`CLAUDE.md`が定める協調プロトコルが、同一セッションの中で並行して「指示」として扱われている状態になっていた。

今回は読み取り専用の調査だったので実害はなかったが、他人のテンプレート(特にClaude Code向けの設定ファイルを含むもの)を調べるときに、気づかないうちに2つ目の指示セットを抱え込むことがある、というのは実務上おぼえておく価値のある挙動だと感じた。長く中に居座らず調査を終えたら早めにディレクトリを抜けるのが安全そうだ。

## `/start`から`/dev-story`まで実際に動かす

手元のPCで対話的な`claude`セッションを開き、クローンしたテンプレートのルートで`/start`を実行した。「どこから始めるか」(アイデアなし/漠然としたアイデア/明確な構想/既存の資産あり)を聞かれ、「アイデアなし」を選ぶと`/brainstorm open`に誘導された。`/brainstorm`は3つの一行コンセプト案を自動提示してきて、その中から「墜落寸前の衛星リレー局をデブリ場から部品を回収して修理し、軌道減衰タイマーが0になる前に全システムを復旧させる」というゲーム「Signal Lost」を選び、対話形式で一枚物の`design/game-brief.md`を生成した。

続く`/setup-engine`では、Unity経験がある旨を答えるとUnityが即決された。最新版をWebSearchで調べたうえで、手元に実際にインストールされているUnityエディタのバージョンをPowerShellで直接プローブしてきた。

```
$ Get-ChildItem "C:\Program Files\Unity\Hub\Editor" -Directory
Name
----
6000.2.11f1
```

最新LTS(6000.3)と実機の既存バージョン(6000.2.11f1)の差分を検出し、どちらを使うか3択で確認された。既存バージョンを選んだところ、テンプレート同梱のエンジンリファレンス文書がすでに6.3 LTSを前提に書かれていることも検知し、参照文書を書き換えるのではなく「実際のバージョンを記録し、差分を`project.yaml`に明記して両立させる」という対応を提案してきた。整合性検証スクリプトもこの差分を`[DIFFERS]`として実際に検出し、マージ判断はこちら側に委ねられた。

`design/game-brief.md`のMVPリスト6件から、`/create-stories`が各項目を1ストーリーずつ構造化した6本のストーリーファイルを自動生成した。`/dev-story`は各ストーリーの実装を`engine-programmer`などのサブエージェントへ委譲し、実装前に毎回「この設計でこのファイルに書いていいですか」と確認を挟んでくる。実装後には別の`unity-specialist`サブエージェントへ「Unity APIの使い方が現行バージョンに対して正しいか」というレビューだけを依頼する2段階構成になっており、実際にこのレビューで`UIDocument.rootVisualElement`の取得タイミングのバグと、生成UXMLの不正な属性の2件を発見し、実装担当エージェントへ差し戻して修正させていた。

Unityの実機プロジェクトがまだ存在しない段階だったため(次節で詳述)、「実際に起動してスクリーンショットを撮る」工程は毎回正直に`NOT VERIFIED`として記録され、UIストーリー(勝敗画面)は`/story-done`の時点で一度**正直にBLOCKED判定**になった。「パースが通ることと実際に動くことは別物」というテンプレートの設計思想が、スローガンではなく実際に機能しているのを確認できた。

## 一番詰まった点: WSL上のリポジトリでUnityが起動を拒否した

ここでCCGS自体とは別の、環境固有の壁にぶつかった。筆者の作業リポジトリはWSL(WindowsのLinux環境)側にあり、そこにUnityプロジェクトを作ろうとした。

```
Aborting batchmode due to fatal error:
The project is on case sensitive file system.
Case sensitive file systems are not supported at the moment.
Please move the project folder to a case insensitive file system.
```

WSLのファイルシステム(ext4)は大文字小文字を区別するが、Windows版Unityエディタはこれを明示的にサポートしていなかった。対応として、Unityプロジェクト本体はWindowsネイティブのパスに別途作成し、コード(`Assets/`)はリポジトリ側を正として変更のたびに手動でコピーして同期する、という二重管理の運用に切り替えた。プロジェクト作成後、`-batchmode -quit`でコンパイルを確認したところ、6ストーリー分のコードがエラーなくビルドされた。

```
--- DLLs built ---
Name
----
Assembly-CSharp.dll
Assembly-CSharp-Editor.dll
```

WSLで開発していてUnity(のWindows版エディタ)を併用する読者が、同じ条件でそのまま再現しうる制約だと思うので、ここは失敗ログも含めてそのまま記録しておく。

## ストーリーの範囲外だった「実際に遊べるようにする」統合作業

6本のストーリーはそれぞれ個別のロジッククラス(タイマー・デブリ・運搬・ステーション・修理・UI)を作るだけで、プレイヤーを動かしてシーン上で実際に遊べるようにする統合作業(プレイヤー操作・カメラ・シーン配置)はどのストーリーの範囲にも含まれていなかった。これはテンプレートの設計通りで、この統合レイヤーは「どのストーリーの正式スコープでもない追加作業」として明示的に確認したうえで直接実装した。

ここでUnity初心者でなくても踏みやすい実務的なバグに3つ遭遇した。1つ目は片付け忘れによる二重初期化で、勝敗画面のテスト用オブジェクトをシーンに残したまま本番用オブジェクトを追加し、同じインスタンスに対して初期化処理が2回呼ばれて例外になった。2つ目はカメラの設定漏れで、デフォルトのMain Cameraがパースペクティブのままだったため、プレイヤー以外のオブジェクトがほぼ画面外に出てしまっていた。3つ目が一番厄介で、エディタスクリプト(編集時に実行するメニュー項目)の中で生成した一時的なスプライトオブジェクトへの参照が、Playモード突入時のドメインリロードで失われ、該当オブジェクトが画面上で透明になっていた。一方、`MonoBehaviour.Awake()`(実行時)で同じように生成したプレイヤーのスプライトは問題なく表示されており、「編集時に生成した一時アセット」と「実行時に生成した一時アセット」とでドメインリロードをまたいだ生存期間が異なるという非対称な挙動だった。最終的にスプライトの割り当てをすべて`Awake()`内のランタイム生成に統一して解決した。

これらをすべて解決したのち、実際にプレイヤーを動かしてデブリをスキャンし、部品を回収し、ステーションで修理する一連の操作が成立し、全システムを修理すれば勝利画面、修理しきる前にタイマーが0になれば敗北画面が表示されることを、スクリーンショットで確認した。

## まとめ

CCGSが主張する「パースが通ることと実際に動くことは別物」「画面の変化を伴う修正は実際に起動してスクリーンショットを残すまで完了にしない」という検証哲学は、実際に`/story-done`のBLOCKED判定として機能していた。一方で6本のストーリー単体では「実際に遊べるゲーム」にはならず、その統合作業はテンプレートのスコープ外であり、結局は従来どおり一行ずつデバッグログを足しながら原因を切り分ける必要があった。49体のエージェント・74個のスキルは「設計からコードへの変換と検証」を高い精度で担ってくれる一方、「実際に動かして遊んでみて、何かおかしいときに原因を探る」という最後の工程は、今回確認した範囲では人間の目と反復作業に最後まで依存していた。

もう一つ収穫だったのは、CCGS自体ではなくClaude Code自体の挙動として見つけた"CLAUDE.md auto-discovery"だった。他人のテンプレートをクローンして`cd`しただけで、そのディレクトリの`CLAUDE.md`(と`@`参照先)がこちらの指示として自動的に読み込まれる。検証のための一時的な調査でも、気づかないうちに相手の協調プロトコルを指示として抱え込むことがある、というのは実務上おぼえておく価値のある挙動だった。
