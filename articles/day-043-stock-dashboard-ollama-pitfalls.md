## これは何を試した記事か

[ZhuLinsen/daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis)(MIT License)は、中国A株・香港・米国・日本・韓国・台湾の株式をLLMで分析し、「買い/様子見/売り」の判定・スコア・トレンド・リスク要因をまとめた「決定ダッシュボード」を生成するOSSである。
株価データ自体はAkShare/Baostock/YFinance等の無料ソースで取得でき、LLM呼び出しもGemini無料枠かローカルOllamaのどちらかで追加の有料APIキーなしに試せる、という触れ込みだった。

筆者はこれをローカルPCで実際に動かし、日本株(トヨタ自動車 7203.T)・米国株(Apple AAPL)・中国株(貴州茅台 600519)の3銘柄を対象に、オフラインテスト→データ取得のみの`--dry-run`→LLM判定込みの本実行、という順で検証した。
LLMにはAPIキーが要らない、無料で動くローカルOllama(`qwen2.5:7b-instruct`)を使い、追加の課金は一切していない。

結論を先に書くと、**ツール自体は実際に動き、3銘柄とも決定ダッシュボードを生成できた。** ただしその過程で、「`--dry-run`なのにLLMを呼んでいる」「市場統計の取得が全滅した結果の『0』を、まるで本物の統計であるかのように断定的な文章にしていた」「ローカルの7Bモデルでは出力の過半が具体性を欠いたプレースホルダーのままだった」という、実際に手を動かして初めて気づいた3つの挙動があった。

- 出典: https://github.com/ZhuLinsen/daily_stock_analysis (MIT License)
- 日本語記事件数(2026-11-09時点、Zenn/Qiita/note検索): 0件

**本記事および本ツールが出す判定(買い/様子見/売り)・スコア・損切りラインは、あくまで技術的な動作確認であり、投資助言ではない。**

## セットアップ: オフラインテストは8,476件全てパス

```bash
git clone https://github.com/ZhuLinsen/daily_stock_analysis.git
cd daily_stock_analysis
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

依存のインストールは問題なく完走した。
リポジトリ自身が案内しているオフライン単体テストも実行した。

```
$ python -m pytest -m "not network"
========= 8476 passed, 4 deselected, 664 warnings in 735.24s (0:12:15) =========
```

約12分かかったが、8,476件すべてパスした。
テストで担保された範囲は健全だということである。

`.env`にはGemini無料枠キーではなく、ローカルに既にあったOllama(`qwen2.5:7b-instruct`)を設定した。

```dotenv
OLLAMA_API_BASE=http://localhost:11434
LITELLM_MODEL=ollama/qwen2.5:7b-instruct
```

## `--dry-run`は、実は完全にLLMを呼ばないわけではなかった

`--help`や`README`は、`--dry-run`を「データ取得のみ、LLM呼び出しなし」と説明している。

```bash
python main.py --dry-run --stocks 7203.T,600519,AAPL
```

ログを見ると、**個別銘柄のAI分析は確かにスキップされていた。**

```
[AAPL] 跳过 AI 分析（dry-run 模式）
[7203.T] 跳过 AI 分析（dry-run 模式）
[600519] 跳过 AI 分析（dry-run 模式）
```

データ取得自体も問題なく動いた。
日本株・米国株はYahoo Financeへ、中国株は東方財富のAPIへと、市場ごとに適切なデータソースへ自動でルーティングされ、実在する直近の株価(600519の直近3営業日の終値1453.00/1444.99/1439.00元など)を取得できていた。

ところが、**`--dry-run`を付けても「大盘复盘」(市場全体のレビュー)機能だけは実行され、Ollama経由で実際にLLMが呼ばれ、984文字のレビュー文章が生成されていた。** `reports/market_review_20261110.md`というファイルがちゃんと作られている。
個別銘柄分析と大盘复盘とで、`--dry-run`の扱いが違う、という実際の挙動である。

## 市場統計が全滅すると、「0」が嘘をつく

その大盘复盘のログを追うと、市場全体の騰落銘柄数・出来高統計を取る`get_market_stats`の段階で、用意された6つのデータソースが次々と失敗していた。

```
[efinance] 获取指数行情失败: Expecting value: line 1 column 1 (char 0)
[MarketStats] ... provider=AkshareFetcher ... action=request_timeout elapsed=30.05s
[MarketStats] ... provider=AkshareFetcher ... action=request_timeout elapsed=30.02s
[MarketStats] ... action=complete status=empty purpose=market_review:cn
```

東方財富はJSONパースエラー、Akshareは2つの異なるAPIでそれぞれ30秒タイムアウト、残りのPytdx/Baostock/Yfinance/Tencentはそもそも対応データを持たず即座に空振り——**用意された6つのデータソースが全滅し、市場統計はまるごと取得できなかった。**

それにもかかわらず、生成された`market_review_20261110.md`にはこう書かれていた。

> 今日市场成交额为0亿元，成交极度低迷，表明市场资金情绪偏弱。涨跌家数为零，涨停和跌停个股也为零，显示市场缺乏明显的短线风险偏好。

**取得できなかった結果の「0」を、まるで実際に出来高がゼロだったかのように断定的な文章で説明していた。**
LLMに渡されたプロンプト自体が「0」という具体的な数値しか渡さず、「取得に失敗した」という文脈を渡していなかったためだと考えられる。
株価情報を扱うツールとして、「データが無い」と「実際にゼロだった」を区別できていないのは、読者が実際に使う際に気をつけたい挙動だった。

## 本実行: 3銘柄とも完走したが、2銘柄はプレースホルダーのままだった

LLM判定込みの本実行も試した。

```bash
python main.py --stocks 7203.T,600519,AAPL
```

パイプラインのサマリーは「成功: 3, 失败: 0, 耗时: 58.13 秒」。
3銘柄とも処理が完走し、決定ダッシュボード`reports/report_20261110.md`が生成された。

ただしログには、LLMの応答が期待するJSONスキーマに一致しない事象が複数回記録されていた。

```
[LiteLLM] ollama/qwen2.5:7b-instruct failed: invalid_json at validation for backend litellm
[LLM JSON] 贵州茅台(600519): all models returned invalid JSON, using text fallback
AnalysisReportSchema validation failed; continuing with raw parser contract: 2 validation errors
[LLM完整性] 必填字段缺失 [...]，已占位补全，不阻塞流程
```

ツール側にリトライとプレースホルダー補完というフォールバック機構があるおかげでパイプライン自体は止まらず、「成功」として扱われる。
ただし実際に生成されたダッシュボードの中身を見ると、**3銘柄のうち2銘柄(トヨタ自動車・貴州茅台)の「一句話決策」は、具体的な理由を欠いた「分析完成」という汎用文言のままで、「止损位」(損切りライン)も「待补充」(未補完)のままだった。**

AAPLだけは次のような具体的な一文が生成されていた。

> 持有观察：市场资金流服务暂不支持，买入结论缺少资金面确认，先按观察处理。

3銘柄とも最終的な評点は揃って「评分 50・持有・震荡」という同一の結果になっていた。
Gemini等のより高性能なモデルを使った場合と比べ、ローカルの7Bモデルではスキーマ適合率・判定内容の具体性が下がる可能性がある、ということを実際の出力で確認した形になる。

一方で、各銘柄のダッシュボードには「数据限制: 量能数据缺失、筹码结构数据缺失、quote: fallback、technical: partial」のように、どのデータが欠けているかを明示する欄があり、個別銘柄レベルではデータ欠損を隠さず開示する設計にはなっていた(前節の大盘复盘とは対照的な点である)。

## 本実行後の2回目の大盘复盘が、9分以上応答なしで止まった

本実行では銘柄分析が終わったあと、大盘复盘も再度実行される。
最初の`--dry-run`実行時、大盘复盘のLLM生成は19秒で完了していた。
ところが本実行での2回目の生成は、セクター/コンセプトランキング取得(今回はキャッシュが効いて数秒に短縮)のあと、LLM呼び出しの段階で進行が止まり、**600秒のタイムアウトで強制終了されるまで応答が返らなかった。**

Ollama自体が無応答になっていたわけではないことは、タイムアウト直後に別途`curl`でOllamaの生成APIを叩いて確認済みである(0.24秒で応答が返った)。
原因はOllama自体の不調ではなく、大盘复盘側のリトライ・検証ロジックか、同一セッション内で2回目のLLM呼び出しを行う際の何らかの資源競合によるものと推測されるが、ソースコードの深追いまではできておらず断定はしない。
再現性のある挙動として、そのまま記録しておく。

## まとめ

- Routine(クラウドの自動実行環境)が報告していた3つの制約(ネットワークブロック・LLM認証情報の欠如・コード実行権限)は、いずれもローカルPCでは再現しなかった。オフラインテストは8,476件全てパスした。
- `--dry-run`は個別銘柄のAI分析はスキップするが、市場全体のレビュー(大盘复盘)のLLM呼び出しはスキップしない、という文書の説明とは異なる実際の挙動を確認した。
- 大盘复盘は、市場全体の統計データソースが全滅した際、取得失敗の結果を「0」としてLLMに渡してしまい、生成文章がそれを実際の市場統計であるかのように断定的に説明する、という信頼性上の懸念を実際に確認した。
- 本実行(LLM判定込み)は3銘柄とも完走し決定ダッシュボードが生成されたが、ローカルの7Bモデルでは出力JSONのスキーマ検証エラーが頻発し、3銘柄中2銘柄は具体的な分析内容を欠いたプレースホルダーのまま出力された。
- 本実行後の2回目の大盘复盘生成が、Ollama自体は正常なまま9分以上応答なしで止まり、タイムアウトで強制終了される、という再現性のある挙動も観測した。

無料・ローカルで動くという点は確かにその通りだったが、「とりあえず無料のローカルモデルを挿せば同じ精度が出る」わけではなく、データ欠損の扱いやモデルの出力安定性には、実際に動かして初めて見える落とし穴がいくつもあった。
